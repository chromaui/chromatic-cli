What this audit is

A fresh hole-hunt after the rsbuild work landed. It re-ran every standing matrix, ran the structural matrix on rsbuild for the first time, reconciled twelve earlier audit documents against the code at HEAD, and read the whole v2 tree looking for change classes that move no hash.

The standing coverage is completely green, and that is the point. All 15 gating runs pass and all 372 unit tests pass, so nothing below was visible from the coverage the project already had. Every finding is something the current instruments cannot see.

How this was measured

Behaviourally wherever possible, per the map's standing rule: never walk the written manifest to ask what is covered, because pruneSyntheticFiles holes it by design. Coverage claims here come from building a manifest, making a real edit, rebuilding the manifest, and diffing — or from chromatic turbosnap-bail, which runs the production traceChangedFiles.

  • Standing matrices — bail-matrix.sh, parity.sh and attribution-matrix.sh across five fixtures, plus matrix.sh across three. Run sequentially: the fixture is shared and each script reverts with git checkout.
  • Structural matrix on rsbuild — structural-probe.sh ui-rsbuild, which rebuilds Storybook per case. Never run on any rsbuild generation before this audit.
  • Graph completeness against disk — a new check: enumerate every source file on disk under each fixture's src/ and ask whether the manifest covers it. The harness has no such probe; it is what surfaced the Vite asset hole.
  • Synthetic name-only stats transforms — the map's cheapest instrument, used to isolate "the graph is wrong" from "the spelling is wrong" without a rebuild.
  • Four parallel code audits and one reconciliation pass over manifest/graph, outOfGraphFiles/storybookFiles, statsAnchor/paths, and the guard ladder plus production callers.

The fixture repo was left byte-identical: after the structural probe, ui-rsbuild's manifest regenerates to ce4b5cbeecf3013e, 3 stories, 203 files — the same bytes as before the run. Two tracked fixture edits that predated this audit (a ui-webpack/.storybook/main.ts reformat and a lockfile refresh) were committed as 063187a so the gating scripts would run at all; six untracked probe leftovers were moved out of .storybook and .storybook/static, where they were silently inflating the config and static file counts.

Two premises this audit falsifies

1. The v1 fallback is not healthy on rsbuild builders 1.0.3 and 2.1.6

The map treats every rsbuild finding as P1/P2 rather than P0 on the stated basis that "every failure found is a bail, not a miss — the v1 fallback is healthy on rsbuild, so the cost is v2's benefit, never a missed snapshot." That basis does not hold on the two unshimmed generations.

Measured with chromatic trace, the harness's own v1 instrument:

ui-rsbuild      (builder 3.4.0)  Button/Button.tsx      -> ["…/Button.stories.tsx"]
ui-sb8-rsbuild  (builder 1.0.3)  Button/Button.tsx      -> []
ui-sb8-rsbuild  (builder 1.0.3)  UserCard/UserCard.tsx  -> []
ui-sb9-rsbuild  (builder 2.1.6)  Button/Button.tsx      -> []

The mechanism: rspack concatenates a single-importer component into its story's record and exposes the member only through nameForCondition, leaving modules[] empty. v1 expands concatenation members from modules[], which webpack populates and rspack does not, so v1 never sees the file: 

ui-webpack       ./src/lib/Button/Button.stories.tsx + 1 modules
                 modules: ["…/Button.stories.tsx", "…/Button.tsx"]   -> v1 finds Button.tsx
ui-sb8-rsbuild   ./src/lib/Button/Button.stories.tsx + 1 modules
                 nameForCondition: /abs/…/Button.tsx,  modules: []   -> v1 finds nothing

And v1 does not bail on it: getDependentStoryFiles has no guard for a changed file that matches no module name, so it returns status: 'traced' with an empty story set. A real build editing only that component would snapshot zero stories. Most components in a real project have exactly one importer, so this is not an edge case on those generations.

Consequence for the map: on builders 1.x and 2.x — roughly 37 projects and 25 accounts per the version survey — a v2 bail hands the build to an algorithm that silently under-captures. Any rsbuild bail on those generations is a candidate missed snapshot, not a mere loss of v2's benefit. v2 gets these cases right, so this is also the strongest evidence yet for shipping v2.

2. Asset imports are not "measured correct for every builder"

The map's Out of scope section records that "the audit also newly measured CSS and asset imports (a stylesheet and an SVG imported from a component) as correctly hashed and story-attributed — a first result for every builder, and no hole." The SVG result does not hold on Vite, and the rsbuild fixtures have no such case at all, so the generalisation was never supportable.

See F2. This is what the disk-versus-manifest completeness check surfaced.

Under-capture: changes that move no hash

This is the only class that costs a customer a missed visual bug. v2 is monitoring-only today, so none of these change a build's outcome yet — but each one is an unsafe answer, and the switch is the point.

F1 — A wrong sibling anchor is unguarded on the default build path

P0confirmed empiricallyall builders
Where
v2/statsAnchor.ts:114-128 (getStatsFileOutsideProject) interacting with tasks/build/setSourceDirectory.ts:27.
Mechanism
For two same-builder sibling packages, getBuilderMismatch returns no verdict and getUnresolvedSourceModules resolves cleanly, so statsFileOutsideProject is the only witness left — the comment at statsAnchor.ts:101-104 says exactly that. That witness works by finding the Storybook project that owns dirname(statsPath). But when the CLI builds Storybook itself and no --output-dir is given — the default path — the build lands in tmp.dir({ prefix: 'chromatic-' }), an OS temp directory with no owning project. The witness returns undefined, and nothing else asks the question.
Failure scenario
Monorepo, chromatic --only-changed --storybook-base-dir packages/ui-sb9-rsbuild where the real project is packages/ui — a typo, a stale copy-paste, or an Nx target that changed directory. Because current-generation rsbuild and every Vite builder emit purely relative module names, they resolve happily at the wrong root and the manifest keys stay ./src/…, so they match Storybook's importPath byte for byte and the Index accepts them. Every hash is read off the wrong package's bytes, and no change in the real project ever moves anything.
Evidence
On a purpose-built two-sibling fixture with a temp-directory stats path: no bail, every section populated, and after a real visual edit to the correct package the wrong-anchor manifest is unmoved (a83c6891bfe39d19 both times) while the correct-anchor one moves (7d7a4d4ff657da28 → 88bc557f09f12ba4). Also reproduced on real fixtures: ui-rsbuild's stats anchored at ui-sb9-rsbuild yields 3 stories, 4 config files, 203 files and no bail — indistinguishable from a correct manifest.
Why this is the witness that matters
statsFileOutsideProject was added specifically to close this case. unseen-inputs-audit.html G2 measured that a wholly unrelated anchor already failed safe and argued the real risk was a structurally similar sibling, whose module names are byte-identical. That is the case this witness exists for — and it is the case the default build path leaves open. (The "unrelated anchors fail safe" half does not hold either; see F9.)
Margin
Exactly one condition: whether dirname(statsPath) has a .storybook ancestor. --output-dir or --storybook-build-dir closes it; the default opens it. Two existing tests each pin half of this and their combination is untested (statsAnchor.test.ts:104 and :150).

F2 — Assets referenced by new URL(…, import.meta.url) are hashed nowhere on Vite

P0confirmed behaviourallyvite
Where
v2/manifest.ts:351-385 (hashFiles). The hashed set is exactly {module.nameForCondition ?? name} ∪ module.modules[*] ∪ reason.moduleName, plus outOfGraphFiles' config and static directories. Nothing else in v2 hashes a source file.
Mechanism
Vite resolves new URL('./logo.svg', import.meta.url) at transform time into a URL string, so the asset produces no stats module and no reason. It is therefore in no hashing home at all — not storyReachable, not previewSubtree, and not <storybookGlobals> either, because the catch-all is derived from hashes (storybookFiles.ts:83) rather than from the file tree.
Failure scenario
Edit the SVG a story renders. The rendered snapshot changes; nothing recaptures.
Evidence
packages/ui/src/lib/PathDerived/PathDerived.tsx renders exactly this. Appending a byte to logo.svg and regenerating: 
ui           storybookHash SAME    | stories changed 0 | storybookFiles changed []
ui-webpack   storybookHash CHANGED | stories changed 2 | storybookFiles changed []
The disk-versus-manifest check finds it directly: across five fixtures the only uncovered source files are src/index.ts — a deliberately unreferenced control — and, on ui alone, src/lib/PathDerived/logo.svg. It appears nowhere in the Vite stats (zero matches for logo), while webpack emits it as a module.
Guard
None. No emptiness check can see it: the sections it would belong to are not empty.
What v1 does
Misses it too — chromatic trace on the same file returns [] on ui and the two correct stories on ui-webpack. So this is a shared blind spot rather than a v1 → v2 regression. It is still the class v2 exists to close, and it is unmeasured on rsbuild, whose fixtures have no such case.

F3 — Query-decorated stats names are silently un-hashed, and v1 handles them deliberately

P0code + v1 comparisonwebpack / rspack / vite
Where
v2/paths.ts:26-28, 48-58, 81-84 and v2/manifest.ts:345-349.
Mechanism
normalizeStatsPath and resolveStatsPath strip only + N modules and a leading ./. There is no handling of a ?query suffix, a ??ruleSet[…] segment, a !-separated loader chain, or a webpack:// prefix. So ./src/foo.component.html?ngResource resolves to a path that does not exist, statSync declines it, the file never enters hashes, and the roll-up contributes the constant '' for it (graph.ts:29). pruneSyntheticFiles then removes the node, so the omission is invisible in the written manifest too.
Why this is a regression, not a shared gap
v1 strips it on purpose: v1/getDependentStoryFiles.ts:106 carries URL_PARAM_REGEX with the comment "Trim query params such as ?ngResource which are sometimes present", and a regression test at v1/getDependentStoryFiles.test.ts:258-264 using that exact name as a concatenated inner module. v2 has no query handling anywhere.
Failure scenario
Angular Storybook on webpack or rspack. The stats carry ./src/foo.component.ts + 2 modules whose members include ./src/foo.component.html?ngResource. A developer edits only the template. Every hash is byte-identical; v2 says nothing changed. v1 traces the file to its story and captures it. Same shape for Vue SFC sub-modules (?vue&type=style) and for ?raw / ?url / ?inline / svgr imports.
Why it is not live on the fixtures, and how narrow that is
Exactly one fixture carries a decorated name — ui-webpack's css-loader/…??ruleSet[1].rules[4].use[1]!./src/lib/PathDerived/styles.module.css — and it survives only because moduleFileNames prefers nameForCondition, which webpack spells as the bare resource path. That defence does not exist on the builders that matter most: Vite and builder-rsbuild 3.4.0 emit no nameForCondition at all, so on those, name is a module's only spelling and any decoration reaches the resolver verbatim. The comment at paths.ts:108 ("rspack puts the real file name in nameForCondition") already stopped holding for the current generation.

F4 — A staticDirs entry that is a file, or carries a :to suffix, is silently unhashed

P0confirmed empiricallyall builders
Where
v2/outOfGraphFiles.ts:170-190 (listFilesRecursively), reached from :66-76; and lib/getStorybookMetadata.ts:240-248 (findStaticDirectories).
Mechanism
The walker assumes every derived entry is a directory. realpath(file) succeeds, then readdir(file) throws ENOTDIR, which the catch at :189-190 swallows as "contributes nothing" — the same treatment as a missing directory. Storybook supports both shapes: its parseStaticDir special-cases statSync(staticPath).isFile() and serves the file at its basename, and it splits a string entry on its last colon into from/to. findStaticDirectories passes the whole string through, so staticDirs: ['../public:/assets'] becomes the nonexistent path public:/assets.
Failure scenario
staticDirs: ['../other', '../public/logo.png'] → <staticFiles> holds only ./other/x.txt. Editing public/logo.png, a served asset, moves no hash. With ['../other', '../public:/assets'] the whole public tree is invisible.
Guard
None in the mixed case. noStaticFiles only fires when every entry resolves empty, and unresolvedStaticDirectories needs staticDirsDeclared, which is only ever set on the prebuilt path.
Note
Two bugs sharing one symptom: the walker cannot hash a file, and the derivation cannot parse the colon form.

F5 — The static-dir cycle guard is a global visited set, so it drops non-cyclic duplicates and races

P0confirmed empiricallyall builders
Where
v2/outOfGraphFiles.ts:176-183. visitedDirectories is keyed by realpath and shared across the whole walk, including sibling branches, rather than tracking the current ancestor chain.
Mechanism
Two distinct served paths that resolve to the same real directory are walked once, and which spelling wins depends on which realpath promise settles first inside the Promise.all at :192-207.
Failure scenarios
On the tree public/{v1/a.txt, v2/a.txt, current -> ./v2}:
  • Under-capture. Retargeting public/current from v2 to v1 — a real change to everything served under /current/ — leaves <staticFiles> byte-identical at e25c02e01c825c8d.
  • Nondeterminism. 60 walks of an unchanged tree produced two different key sets and two different roll-up hashes: 58× [v1/a.txt, v2/a.txt] and 2× [current/a.txt, v1/a.txt]. About 3% of builds on that tree would move <staticFiles> and storybookHash and force a full recapture for no reason — and in the minority outcome the real directory public/v2 is absent while the symlink spelling stands in for it.
Fix shape
The guard only needs to break cycles, which require a symlink pointing at an ancestor. Tracking the ancestor chain instead of a global set fixes both symptoms, still passes the existing cycle test (outOfGraphFiles.test.ts:254-266, whose loop target is an ancestor), and costs only bounded duplicate work — the direction this project prefers.

F6 — A build-script -c <dir> flag makes staticDirs derivation read the wrong config

P0code + partial empiricalinput boundary
Where
lib/getStorybookMetadata.ts:316-327 versus lib/turbosnap/index.ts:75-76.
Mechanism
getStorybookMetadata loads main from storybookConfigDir ?? '.storybook' and resolves staticDirs against that same literal — it never consults the -c flag that findConfigFlags extracts from the build script in the same Promise.allSettled. v2's getV2Input does consult it. So the two inputs handed to hashOutOfGraphFiles come from two different config directories.
Failure scenario
Build script storybook build -c ./config/sb, no --storybook-config-dir, and ./config/sb/main.ts declaring staticDirs: ['../../public']. readMainConfig('.storybook') fails, so findStaticDirectories returns {} and staticDirs is empty. <storybookConfig> correctly hashes ./config/sb/**, but <staticFiles> is omitted entirely and any asset change is invisible. The rarer variant is worse: with a stale .storybook/main.ts also present, static dirs are read from the wrong config and resolved against the wrong base, so v2 hashes directories the build never served.
Guard
None. staticDirsDeclared is false outside the prebuilt path, and noStorybookConfigFiles is satisfied by the correct -c directory. The same mainConfig === undefined also makes findBuilder return 'unknown', which disables the builder-mismatch anchor check.
Scope
This is the input boundary, chartered on TurboSnap 2.0 — Next Phase, not on the rsbuild map.

F7 — PREVIEW_CONFIG_PATTERN hardcodes .storybook, so a custom config dir mis-attributes shared preview dependencies

P1reproducedall builders
Where
v2/storybookFiles.ts:12, used at :66. collectStorybookFiles takes no configDir, and manifest.ts:147-152 does not pass one — even though configDir is threaded into hashOutOfGraphFiles a few lines later.
Mechanism
With a config directory not literally named .storybook, no storybookFiles entry is created for the preview and previewSubtree is empty. A file the preview imports and some story also imports — a theme, a token file, a decorator helper — is then storyReachable, so it is excluded from <storybookGlobals>. Its change moves only that one story's hash, even though the preview makes it affect every story.
Failure scenario, reproduced
-c config, config/preview.ts importing src/theme.ts and setting a global parameter from it, Button.stories.tsx also importing it, Badge.stories.tsx not.
  • configDir = '.storybook': editing theme.ts moves the keyed ./.storybook/preview.ts entry → recapture everything. Correct.
  • configDir = 'config': editing theme.ts moves only Button.stories.tsx. <storybookGlobals> and <storybookConfig> both stay put — the latter hashes config/preview.ts's bytes, not its imports. Badge.stories.tsx does not recapture despite its global parameter changing.
Guard
None, and the test suite currently pins the wrong behaviour: storybookFiles.test.ts:60-70 asserts that ./src/preview.ts belongs in storybookGlobals.

F8 — A plain first-party module becomes a story file on rsbuild when a story component gains an import

P1reproduced twicebuilder-rsbuild 3.4.0
Where
v2/storyContexts.ts's story-importer rule, fed by v2/manifest.ts:118-121's canonicalisation of reason.moduleName.
Mechanism
The rsbuild shim, when it reduces the module list, re-emits each concatenation member as its own top-level record carrying the parent's reasons — which for a story concatenation is the lazy story require-context. So a plain module looks as though the story context imported it directly, and v2's "a file imported by a lazy story context is a story file" rule promotes it. The correctly-reasoned record exists too, under the shim's unprefixed spelling, and normalizeStatsPath canonicalises both to the same key and unions their reasons — so the context reason always survives.
Evidence
Found by structural-probe.sh ui-rsbuild new-import, then reproduced independently by hand. Adding src/lib/Button/spacing.ts and importing it from Button.tsx: 
storyFiles: [
 "./src/lib/Badge/Badge.stories.tsx",
 "./src/lib/Button/Button.stories.tsx",
 "./src/lib/Button/spacing.ts",      <-- not a story
 "./src/lib/UserCard/UserCard.stories.tsx"
]
The two records, from the same stats file: 
./src/lib/Button/spacing.ts   reasons: ["./src/lib|lazy|…|include: /…\.(mdx|stories\.(js|jsx|ts|tsx))$/|…"]
  src/lib/Button/spacing.ts   reasons: ["src/lib/Button/Button.tsx"]
Why it is not an under-capture
Recapture stays correct — Button's story hash still moves, storyReachable goes 151 → 152 and the bucket is unchanged. The damage is a story key that Storybook's index can never match, sent to the Index as though it were a story, plus a story count that misreports. That is the unmatchable-key class the map has reasoned about twice; the existing fix does not apply, because it is gated on node_modules and this key is first-party.
Fix shape
The same switch the node_modules refusal already reads: the context's own include glob demands .stories.* or .mdx, so the glob's own intent excludes spacing.ts. Only the baseline concatenation is small enough to hide this — + 1 modules does not trigger it, + 2 modules does, which is why no standing matrix has ever seen it.

Mechanism

F10 — Absolute-spelled stats names erase the anchor evidence before it can be counted

P1confirmed empirically
Where
v2/statsAnchor.ts:175-178 and :162.
Mechanism
getSourceModuleResolution pre-filters candidates with isInside(projectRoot, resolveStatsPath(name, projectRoot)). An absolute name pointing at another package fails that test and is dropped before it can be counted as missing. With sourceModuleCount === 0, line 162 returns "no verdict" even though the stats named 151 files, none of them in the project. v1's checkStorybookBaseDirectory has no such filter, so this is a regression in the ported predicate rather than a faithful port.

ui-sb9-webpack's stats transformed to all-absolute names, anchored at marketing-ui: all 151 candidates dropped, no anchor verdict, and the run is diagnosed by noStoryFiles — which sends a debugger to story globs and require-contexts instead of to the anchor.

F11 — A case-only anchor difference either states something false or builds a chimera

P1confirmed empiricallymacOS default, Windows
Where
v2/statsAnchor.ts:216-228 (isInside/isDisjoint) and v2/paths.ts:57.
Mechanism
existsSync is case-insensitive on macOS and Windows, while path.relative and path.resolve comparison are case-sensitive. So one on-disk directory spelled with different case is judged disjoint from itself.
Evidence
ui-webpack's stats with projectRoot = packages/UI-webpack:
  • With a prebuilt stats path it bails and states something untrue — "the stats file lives in the Storybook project …/ui-webpack, which is not …/UI-webpack". It is the same project, so a debugger hunts for a second Storybook that does not exist.
  • With the default temp-directory stats path there is no bail, but path.relative turns every absolute name into a ../ui-webpack/… key. Story keys spelled that way can never match a Storybook importPath, and the graph splits — module keys from the absolute nameForCondition, importer keys from the relative reason.moduleName — while <storybookConfig> is still read correctly. The result is a manifest that reports success and is internally inconsistent.

F12 — An unreadable or vanished config/static file is reported as our own internal error

P1confirmed empirically
Where
v2/outOfGraphFiles.ts:142 → v2/fileHashes.ts:25 → lib/getFileHashes.ts:62-72, surfacing at v2/index.ts:75-77.
Mechanism
The walk filters entries by type, but the hashing step has no equivalent of the graph path's statSync guard. Any single open failure rejects the Promise.all, throws out of buildManifest, and lands in internalErrorBail(error, 'manifestBuildFailed', 'buildManifest') — with a Sentry event under that one fingerprint.
Evidence
chmod 000 on one file in a static dir produces EACCES out of hashOutOfGraphFiles; a file deleted between readdir and open produces ENOENT the same way. Neither is our bug, both are environment-caused, and both are indistinguishable from a real defect. There is no subreason for it.
Related
An unresolvable Storybook version (v2/storybookVersion.ts:50,56-58) collapses into the same bucket, including an unguarded JSON.parse. And an EACCES/EIO on a nested subdirectory takes the opposite path — outOfGraphFiles.ts:176-190 returns [], yielding a silently partial section while the sibling files keep both emptiness guards quiet.

Operational and latent holes

F13 — The diagnostic manifest is never written in production, and emits a Sentry event per build

P2confirmed
Where
lib/turbosnap/index.ts:70, v2/index.ts:142-150, v2/manifest.ts:240-245.
Three independent facts
  1. Nothing creates the directory. The only mkdirSync of <sourceDir>/.chromatic in the codebase is tasks/build/buildReactNative.ts:120, and TurboSnap is rejected for React Native. So writeFileSync throws ENOENT, which writeDiagnosticManifest swallows into a Sentry event tagged turbo_snap_v2_diagnostic: writeManifest — one per build. Confirmed against the fixtures: .chromatic is absent under all five storybook-static/ directories even though turbosnap-bail ran against them four times during this audit.
  2. Nothing uploads it even if written. tasks/prepare/validateFiles.ts:52 excludes .chromatic from the upload list, and lib/uploadMetadataFiles.ts:30-41 uploads a fixed list that does not include it. The doc comment at manifest.ts:36-37 ("uploaded as a static file to S3 for debugging purposes") does not hold.
  3. Wrong directory when the output dir deviates. tasks/prepare/index.ts hands TurboSnap the corrected fileInfo, but ctx.sourceDir is only updated after the task, so statsPath comes from the corrected directory while the manifest is aimed at the stale one.
Why it matters
A bail is exactly when the manifest is worth inspecting — that is the stated reason it is written at every exit. Today no bail produces one. Separately, the comment at v2/index.ts:79-81 ("every one of them writes it") is not true of the four pre-manifest exits, which have no manifest to write.

F14 — v2 uploads no hashes on exactly the builds that must serve as hash baselines

P2code readingblocks the switch
Where
lib/turbosnap/index.ts:27-28.
Mechanism
v2 is gated behind v1's preconditions — ctx.turboSnap.unavailable and !ctx.git.changedFiles. A build with no ancestor has no changed-file list, so v2 is skipped and uploads nothing. But that is precisely the build a descendant's Index comparison will use as its baseline. v2 needs hashes on the baseline, which is a different precondition from v1's "I have a diff to trace".
Consequence
Today: monitoring data is systematically missing after every cold start, rebase, or UNAVAILABLE build. After the switch: the first build following each of those cannot be decided by hash.
Scope
The switch is chartered on TurboSnap 2.0 — Final Phase; this is a precondition for it.

F15 — Concatenated-member coverage rests entirely on one optional stats field, with no assertion

P2confirmed by transformrsbuild
Mechanism
On the unshimmed rsbuild generations a single-importer component exists in the stats only as a concatenation member's nameForCondition. moduleFileNames (paths.ts:107-112) is nameForCondition ?? name, so that field is the whole mechanism. On builder 3.4.0 there is no nameForCondition at all — 0 of 268 modules — and 14 concatenated records whose modules[] do not list their real members, so coverage there depends instead on the shim independently emitting a per-file record. Two different mechanisms, one per generation, neither asserted at runtime.
Evidence
Stripping both spellings recursively from ui-sb8-rsbuild's real stats: 
BASE  hash eeeaf231321ba882  stories 3  files 167
STRIP hash ffb4adff5208f856  stories 3  files 164
lost first-party keys: ["./src/lib/Button/Button.tsx", "./src/lib/UserCard/UserCard.tsx"]
Two real components leave the graph, three stories are still detected, and nothing bails. A later edit to either file would move no hash.
Why this is not hypothetical
The shim's reduced record shape is {id, name, modules, reasons} — it drops nameForCondition by construction. It happens to also flatten every module into its own record today, and the map pins that as a semantic requirement ("every attributable real module appears somewhere with a usable filename") tested by comparing full against minimal stats. But that test compares 3.4.0 against itself, where the flattening exists. Nothing pins the unshimmed concatenation shape, and nothing detects the loss at runtime.

F16 — Smaller latent items

P3
--untraced is silently inert in v2
untraced appears nowhere in TraceChangedFilesInput or the v2 tree. v1 removes untraced files from its seed list and from every reason it walks; v2 hashes them and rolls them into every reaching story subtree. The direction is safe (v2 wider), but a documented user option silently stops working.
Partial story detection has no guard
v2/index.ts:277 and :297 both gate on storyFileHashes.size === 0, so nothing notices a graph that yields some stories. Usually that degrades to over-capture, with one leak: a component imported by both a missed story and a detected one is storyReachable, so an edit moves only the detected story's hash. The same shape makes unrecognizedStoryEntry unable to fire for a build with one recognised and one unrecognised generated entry. No fixture reproduces partial detection today — all ten detect 100% of their on-disk story files.
A prebuilt build can be told it declares webpack4
lib/getPrebuiltStorybookMetadata.ts:24-30 lets prebuilt metadata win, and getBuilder defaults a missing project.json builder to 'webpack4'. declaresVite('webpack4') then asserts "the project is non-Vite", so Vite stats bail anchorMismatch/builderMismatch naming a builder the build never used — pre-empting the accurate untrustedBuilderStats. Fails safe; the reason is a fabrication. The harness omits this default and so can never reproduce it.
Input derivation sits outside the isolation boundary
lib/turbosnap/index.ts:41 protects v1 with traceChangedFilesV2(getV2Input(…)).catch(() => {}), but getV2Input is evaluated as an argument, so a synchronous throw inside it escapes the catch and fails the customer's build. Unreachable today; the wrong shape for a monitoring-mode subsystem.

Holes in the instruments

parity.mjs has no verdict for "v1 missed a story v2 caught"

The three cells where v2 and v1 disagree on the older rsbuild fixtures are reported as v2 wider (over-captures — safe). They are nothing of the kind: v1 recaptured zero stories for a direct component edit and v2 recaptured the correct one. The verdict vocabulary — parity, v2 wider, v2 narrower, and v2 MISSES a story v1 caught — has no cell for the mirror case, so v2's strongest result is recorded as a v2 wart and the underlying v1 defect is invisible. This is why the premise in §1 survived.

structural-probe.sh does not gate, and cannot run on rsbuild

  • No exit-code gate. Unlike attribution-matrix.sh, parity.sh and bail-matrix.sh, it prints for a human to read and carries no machine-checked expectations. This is the defect that let one attribution probe measure nothing for months, and it is still present here.
  • It exits 0 after dying. The run aborted at move-path-derived — mv: … No such file or directory, because ui-rsbuild has no PathDerived component — and still reported success. Eight of thirteen cases never ran.
  • Its rspack exclusion rested on a falsified reason. structural-audit.md scoped rsbuild out because it "indexes 0 stories, so every structural probe there only moves the bucket". Story detection was fixed; parity and bail were re-measured on rsbuild; structural was not. That is how F8 stayed hidden — and F8 needs a + 2 modules concatenation, which only a structural case produces.

Fixture coverage gaps

  • The three rsbuild fixtures have 8 source files each against 13 for ui/ui-webpack: no CSS module, no imported SVG, no import.meta.url asset, no PathDerived. So the entire asset and path-derived class is unmeasured on every rsbuild generation, and the eight structural cases that need those files cannot run.
  • MDX is measured nowhere and recorded nowhere. No document names it and no v2 code branches on it. The map lists MDX-on-rsbuild as fog; the reality is broader — MDX story files are unmeasured on every builder.
  • No fixture story references a static asset by URL, so <staticFiles>' mechanism is measured but its consequence is not.
  • matrix.sh's moment row is vacuous on webpack and rspack (a hardcoded Vite path), which is annotated in the script and covered properly by attribution-matrix.sh's dep_key. Not a finding — recorded so a reader of matrix-ui-rsbuild.log's "0 stories changed" does not mistake it for one.

Hypotheses checked and cleared

Negative results, so they need not be re-chased:

  • getStatsRoot preferring the project root cannot pick the wrong root for genuinely repository-root-relative stats: a repo-root build names the config file ./packages/ui/.storybook/preview.ts, which does not resolve under projectRoot. Measured — an anchor at the repo root correctly bails unresolvedSourceModules.
  • Forgetting --storybook-base-dir entirely in a monorepo is correctly diagnosed as unresolvedSourceModules.
  • Webpack loader chains and ??ruleSet[…] are harmless today on all three webpack fixtures and both older rsbuild fixtures — nameForCondition neutralises them, and no reason.moduleName in any fixture carries a loader chain. Recorded as latent under F3.
  • Story files above the project root (../shared/src/Foo.stories.tsx) match Storybook's importPath: prefixInProjectPath implements exactly Storybook's normalizeStoryPath rule.
  • Windows separators round-trip through normalizeStatsPath for the same-drive case; cross-drive is cosmetic, since the node is pruned.
  • A case-insensitive filesystem producing two hash keys for one file is over-capture-neutral: both keys hash the same bytes.
  • getBuilderMismatch does not false-assert on webpack — isBuilderViteStats matches @storybook/builder-vite/, absent from all five non-Vite fixtures, and declaresVite returns no verdict for an unrecognised builder.
  • The { from, to } object form of staticDirs resolves correctly, and its resolution base matches Storybook's own resolve(configDir, directory). F4 is about which config directory and the string colon form, not the base rule.
  • Config/static overlap dedupe is correct — nested static files are removed from the config sweep, and duplicate or nested static dirs collapse. No double-hashing.
  • Dotfiles in the config walk cause no churn on any fixture, so the deliberate absence of ignore rules is not an over-capture in practice.
  • Symlink cycles still terminate. F5 is that the guard is broader than cycles, not that it diverges.
  • storybook/package.json resolves in practice on every fixture layout — 10.6.0-alpha.3, 9.1.20, 8.6.18 — with no ERR_PACKAGE_PATH_NOT_EXPORTED.
  • The STORIES_ENTRY_FILES/CONFIG_ENTRY_FILES asymmetry is not exploitable: an un-catalogued stories entry above a lazy context is caught on the basename and bails unrecognizedStoryEntry.
  • Externals cannot become story files — the resulting node is unhashable, so it is pruned.
  • classifyUploadHashesFailure has no double-reporting or swallowing: the throw path and the resolved-failure path are disjoint, and unknown __typenames fold into invalidResponse by design.
  • Stats with no modules array at all are caught as internalError/anchorCheckFailed.
  • Two stats modules collapsing to one canonical key unions their dependency sets, which is over-capture-safe.
  • pruneSyntheticFiles mutating during iteration is well-defined; no entries are skipped.
  • My own nameForCondition-only strip cleared a false alarm. Removing it from top-level records alone changes nothing, because the nested member copy still carries it. Only the recursive strip loses files — which is what makes F15 precise rather than speculative.

Already known, not re-raised

A reconciliation pass over twelve earlier audit documents found 27 findings closed in code and 8 retracted, mis-attributed, or superseded. Two live items are worth restating because they bound what any CLI-side audit can conclude:

storybookFiles is never sent to the Index

v2/api.ts:84-93 sends buildId, storybookHash and storyFileHashes and nothing else; BuildUploadHashesInput has no field for storybookFiles. So a change confined to a storybookFiles entry — a static asset, main.ts, a preview.* edit, a Storybook upgrade — moves storybookHash while matching no story, and the Index captures nothing where v1 bails. This is the largest live under-capture in the system and no CLI change can close it. It is documented in the code and tracked as a P0 on the Index Fixes page.

Deliberate positions this audit did not reopen

  • No rsbuild builder version floor — declined twice, and the reason is now stronger: both fixes in ca96074a are generation-blind, and 3.3.0/3.3.1/3.3.4 produce a byte-identical manifest.
  • The intermediate-cwd stats root fails safe to v1 and no tooling default produces it.
  • The hoisted-cache asymmetry — accepted from a repo-root build, refused from a package-dir build — is a deliberate, test-pinned choice.
  • package.json and lockfiles stay out of the hashed inputs.
  • The builder-vite version floor and its escape hatch, and the findBuilder/resolvePackageJson builderName defect, are chartered elsewhere.
  • Redundant path normalisation (~30% of buildManifest self time) and the stories×subtree roll-up cost remain deferred, non-blocking. moduleFileNames' new suffix-strip and Set de-dupe have grown the former slightly.
